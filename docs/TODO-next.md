## 经验留档（踩过的坑，勿再走弯路）

### 1. 数据隔离（最重要，曾造成不可恢复的损失）

`_refresh_config()` 会按配置项 `backup_dir` **重建** `self.backup_store`，
所以测试里只赋值 `backup_store` 是拦不住的 —— 必须在 `make_plugin()` 里
把 `backup_dir` 钉进系统临时沙箱（现在就是这么做的 + 有断言），
并且在任何删除/清理类用例前断言「存档根目录确实在沙箱里」。
历史上因为这条，测试把真插件目录里 55 份手动快照删掉了（不可恢复）。
`test_local.py` 的 `[17]` 还加了一条「真插件 `backups/` 前后零变化」的自检。

### 2. 编辑器页面通道（已打通，勿再走弯路）

- 插件页面 SDK 的 endpoint 会被拼成 `/api/v1/plugins/extensions/<插件名>/<endpoint>`；
  该路径由 AstrBot 的 `_call_plugin_extension` 在 `star_context.registered_web_apis` 里匹配，
  匹配不到就是「未找到该路由」。
- 因此**插件必须自己注册 Web API**：
  `context.register_web_api("/<插件名>/config", handler, ["GET","POST"], desc)`
  —— route 必须带插件名前缀，页面只传相对路径 `config`。
- 现有 4 个路由：`config`（GET 读 / POST 写）、`snapshot`（存档动作）、
  `players`（玩家列表 / 存档内玩家 / 改金币）。**加新路由就照这个模式加一条 route spec。**
- ❌ 不要再用「上传文件 + 轮询」通道：真实环境返回 `403 Insufficient API key scope`。
- ❌ 不要再猜 `/api/plugins/<id>/config` 这类路径：那是 AstrBot 自己的接口，不在插件页面权限内。
- ⚠️ 页面里的 `sendCommand()` 会把 `snapshot_` 开头的动作**自动改投到 `snapshot` 路由**并去掉前缀 ——
  名字里带 `snapshot_` 但实际不属于存档的动作（例如 `snapshot_gold`）必须直接 POST 到自己的路由，
  否则会被改写成 `{action: "gold"}` 打到存档接口上（v1.10.0 真的踩到过，靠 `test_editor_ui.js` 抓到）。

### 3. 改 `pages/editor/index.html` 的硬规矩

- **只做最小改动**：先 `read` 再 `edit`，**永远不要用正则整段替换函数**（已经两次把页面写坏）。
- **每改一处立刻跑 `node test_editor_ui.js`**（离线 + 假 SDK 两种通道都会跑）。
- **页面里任何「插件侧才有的清单」都不许写死**（v1.12.1 的教训，代价是站长存不了配置）：
  场景键有 154 个、还会随版本增加，写死的白名单会把合法数据判成红线。
  需要清单就从插件接口拿（`scenes` 端点给了 `scene_total` 和每个场景），
  拿不到时**返回 null 表示不校验**，并且**永远不要拿校验结果去拦整页保存**。
- **保存闸门只拦「这次改过的行」**：`doSave()` → `diffTab(id).dirty` → `problemsInTab(id, true)`；
  没动过的行里的问题走 `stale` 分支只提醒（`tabHealth()` 给标签上的 ⛔/⚠ 供数）。
  报错必须给出「表 · 行号 · 行标识 · 字段 · 原因」，并用 `gotoProblem()` 跳过去 ——
  只说「有内容没填对」等于让站长自己一格格找，历史上就是这么丢掉他的别名编辑的。
- 加标签页时要同步：`TABS`、`TABLE_DEFS`、`state.data` 初始化、
  `test_editor_ui.js` 里的标签数 / 载荷字段数 / 序列化键清单断言。
- `invisible` 是**显示开关**：`_config_schema_to_default_config()` 不看它，
  所有项照样进默认配置；AstrBot 前端的 `AstrBotConfigV4` 用 `l.invisible` 决定要不要渲染那一行。
  所以「隐藏」不会让配置值丢失，也不会让编辑器页面改不了（页面白名单来自 `DEFAULTS`）。

### 4. 配置默认值同步

- `_defaults_fingerprint()` 只对**参与同步**的键做哈希；新增配置项若属于
  「站长自己写的内容」（内容表、命令别名、自定义命令）或纯说明项，
  必须加进 `DEFAULTS_SYNC_EXCLUDE_KEYS`，否则升级时会把站长的编辑覆盖掉，
  也会让指纹变化触发一次全量同步。

### 5. 道具效果键（v1.11.0 的老规矩；v1.13.0 起简化成一处，见 §7）

效果键的白名单在**三个地方**，改的时候一起改，否则会出现「配置里写了但没生效」：

1. `_calc.py` 的 `_parse_effects()` —— `allowed` 元组（真正的解析口，写错的键**静默忽略**）；
2. `pages/editor/index.html` 的 `ITEM_EFFECT_KEYS` —— 页面提示 + 行校验（写错会标红）；
3. `test_editor_ui.js` 会**直接读 `_calc.py` 的源码**断言两边键集合一致，所以漏改会立刻报错。

三种角色的语义（别混）：

- 喂鱼 `meat/spirit/sheen/value_up` → **一次性永久**，落在某条鱼的实例上；
  `feed_bonus` 只抬这条鱼的**投喂次数上限**（`feed_max_uses` + 累计 `feed_bonus`，夹在 0~20）。
- 钓手手气 `buff_quality` → 落在**玩家**身上，`luck_charges` + `buff_casts_left`；
  `_engine.py` 每竿扣一次 `buff_casts_left`，**只有扣到 0 才清 `luck_charges`**
  （彩蛋捡到的手气没有竿数，仍然一竿即清）。**别在喂鱼分支里改玩家状态。**
- 鱼缸装饰 `decorate` → 落在 `player["decorations"]` 列表，每条有自己的 `expire_ts`；
  加成在领取挂机收益时用 `_decoration_bonus()` 现算（时间按真实时间，下线也走）。

### 7. 效果键现在只有一处（v1.13.0）

加一个内置效果键，只需要在 `_effects.py` 的 `BUILTIN_EFFECTS` 里加一行 `EffectSpec`：

* 解析白名单：`load_extensions()` / `_apply_extensions()` 会调 `sync_to_calc()`，
  把键名同步进 `_calc.EFFECT_ALLOWED`（解析实现仍在 `_calc._parse_effects`，
  数值写法与历史版本逐字一致）
* 页面清单：`_editor_bridge` 把 `effect_table()` 塞进 `config` 与 `scenes` 两个接口，
  页面 `applyEffectKeys()` 覆盖内置兜底清单 —— **别再往页面里写死清单**
* 编辑器校验：页面用插件发来的键名判断「插件不认识的效果键」，拿不到就**不校验**
  （宁可漏报，也不能把本来对的行标红 —— v1.12.1 的教训）

配套的坑：

* `test_editor_ui.js` 会去读插件源码比对白名单。白名单从 `_parse_effects` 函数体搬到
  模块级 `EFFECT_ALLOWED` + `_effects.BUILTIN_EFFECTS` 之后，**测试的正则要跟着改**
  （现在同时校验「注册表顺序 == 白名单顺序」）
* `TABLE_DEFS` 是页面加载时建的静态对象，`title` 已经把效果说明快照下来了；
  `applyEffectKeys()` 里要顺手把它同步回来，否则表头 tooltip 还是旧的
* `_effects` / `_calc` 是 `_load_sibling` 按**别名**注册的（`astrbot_fishing_effects`）。
  兄弟模块里要拿对方，必须先查 `sys.modules`，裸 `import _calc` 会拿到另一个实例
  （白名单里没有扩展键，扩展键就解析不出来了 —— 单测里踩过）
* 扩展处理函数的签名固定为 `(*, plugin, player, item_id, key, value)`；
  只有扩展键的道具由插件代劳「消耗一件 + 保存 + 提示」，和内置效果混在一件道具上时
  提示仍由内置分支负责（扩展的文字不单独显示）

### 8. 按钮样式：0 = 灰、1 = 蓝（v1.13.1 更正，别再猜）

**官网取值就是 0 和 1，别自己发明数字。**
《消息按钮》文档写得很死：`render_data.style | int | 是 | 按钮样式：0 灰色线框，1 蓝色线框`
（bot.q.qq.com/wiki/develop/api-v2/server-inter/message/trans/msg-btn.html）。
`botpy` 的 `RenderData.style` 只是个裸 `int`（没有枚举），所以文档就是唯一定义。

* v1.13.1 之前 `_calc.BUTTON_STYLE_ALIASES` 写的是 `default=1 / primary=4` —— 纯猜的。
  后果：标着「默认（灰）」的按钮在 QQ 里是**蓝色线框**，而 `primary=4` 根本不在文档里。
  现在 `default=0`、`primary=1`，`BUTTON_STYLE_DEFAULT = 0`，`_interactions._btn` 兜底也是 0。
* **页面与插件必须用同一套数字**：`pages/editor/index.html` 的 `normalizeButtonStyle()`
  把 `0→default`、`1→primary`，其余数字（2~255）**原样透传**。
  页面认不出的数字绝不能改写成 default —— 那是「保存一次就把玩家的按钮颜色全改了」。
* 改这张表 = 改站长线上按钮的颜色。要改先想清楚：老配置里 `|default` 的按钮会换色。
* 数值样式（`|7` 这种）任何环节都不要翻译、不要四舍五入，官网只保证 0/1 的含义，
  其余数字是「原样透传」，插件不替 QQ 做解释。

### 9. 订单为什么按钓点抽（v1.14.0）

`_roll_orders(level, location_id=None)`：

* 给了 `location_id` -> 候选池 = `_location_pool(location_id)`（**当前钓点**）；
  首选 = 等级品质档内的鱼，补充 = **同一个图**其它品质的鱼。本图这一档不够时用
  同图的鱼补满（`order_count` 不缩水），**绝不跨图** —— 「站在哪儿只能被点哪儿的货」
  是硬约束，不然又会出现「要一条你根本钓不到的鱼」（v1.14.0 之前就是这样：
  池子是全部 232 种，会点到还没解锁的钓点的鱼）。
* `location_id=None` -> 老行为：全鱼池里按品质档抽，补充池为空。
* ⚠️ 抽签顺序不能反：`_order_pools()` 返回 `(首选, 补充)`，**先抽首选、不够再补**。
  直接 `random.sample(首选 + 补充)` 会把等级品质档稀释掉
  （Lv20 站在新手村就会一直点常见鱼）。

换钓点换单（`_ensure_orders`）：

* `expired = (没订单) or 到点了` -> 换一批，并把 `order_move_rerolls` **清零**；
  没到点但 `order_location != current_location` -> 也算要换（`moved`），
  但要受 `order_move_rerolls` 限制（默认 1）。
* ⚠️ 顺序陷阱：一开始写成「只要 `moved` 就 +1」，结果**到点刷新和换图撞在一起**时
  计数被 +1 而不是清零，玩家在新周期里白白少一次换单机会。现在 `expired` 优先判断。
* 换单**不重置** `order_next_ts`（否则来回换图 = 无限刷单）；
  每个周期最多换 `order_move_rerolls` 批，这就是防刷单的那道闸。
* 移动回复只在「本来就有订单 + 真的换了」时才多一行，别在没看过订单的玩家那儿刷屏。

`/钓鱼 去` 与 `解锁并前往` **两处**都要调 `_ensure_orders`（`_cmd_locations` 里
两个 `player["current_location"] = ...` 各一处），漏一个就会出现「换图了订单没跟」。

测试口径：`test_local.py` 的「订单按当前钓点刷新」段 —— 抽 200 批断言零越界、
换图换单 + 计数、上限拦住第二次换图、到点刷新清零、开关关掉完全回老行为、
隐藏生物开关、`order_move_rerolls=0`。**别只测「抽出来的鱼在图里」**，
「不换单」那条路径也要钉住，否则防刷单被改坏了没人知道。

### 10. 水族馆相处机制：方向比强弱更重要（v1.15.0）

站长报的「藤壶怎么把章鱼吃了」不是概率问题，是**规则方向**写错了：
旧版是「狠角色 + 对手（另一个狠角色或紧挨着的邻居），谁 `_fish_power` 低谁没」。
于是养肥的藤壶（`_fish_power` 高）能把章鱼冤死 —— 文案还写成「藤壶把章鱼逼到了角落」，
等于说藤壶是凶手。**温和鱼根本不该有下嘴的能力。**

现在的规则（`_resolve_tank_conflicts`）：

* 只有 `_is_hostile` 的鱼会主动攻击；
* 对手是另一个狠角色 -> 壮的吃弱的（duel，文案「打了一架，X 没了」）；
* 对手是温和鱼 -> 狠角色**必须 `_fish_power >=` 对方**才吃得下，
  否则 `continue` 换下一个狠角色试（小章鱼挨着养肥的大鱼：两条都活着）；
* 温和鱼之间永远无事发生。

坑与约定：

* 一轮最多淘汰一条，淘汰后重新扫描（外层 `for _ in range(len(aquarium))` +
  内层找到能下嘴的就 `break`，靠 `acted` 判断「这轮没人动手」就收工）——
  不要写成「每轮固定换掉一条」，否则同一个狠角色会被反复配对。
* **不要用 `diff`（拉线难度）当捕食者信号**：实测章鱼 diff=0.0、月华水母 diff=0.62，
  两者完全分不开。分类只有 `HOSTILE_KEYWORDS` 一张表。
* `_parse_word_list("")` 返回**内置默认**（不是空元组）：所以「清空关键词 = 恢复默认」，
  页面文案也照这个说。想让缸里彻底没有狠角色，只能写一个匹配不到任何鱼名的词。
* 页面侧要改这张表，靠 `NUMBER_KEYS` 第 5 位 `true` 标成文本行：
  `cellHtml` / `onCellInput` / `validateRow` / 对齐 class 都判了 `row.text`，
  **漏一处就会出现「需要是数字」或者把逗号串 `Number()` 成 NaN**。
  加断言见 `test_editor_ui.js`「文本行…」四条。
* ⚠️ 探针里 `import _editor_bridge as eb` 拿到的是**另一份模块实例**
  （`DEFAULTS` 没注入 → `number_whitelist()` 返回 0 条，看着像「白名单没这个键」）。
  要验证页面通道，必须用插件按别名加载的那份：`sys.modules["astrbot_fishing_editor_bridge"]`。
  同样的坑 `_calc` / `_effects` 也有（见 §7）。

### 11. 页面校验用的是插件下发的清单 —— 下发什么就得包含什么（v1.15.1）

站长报「UI 里洗髓丹那行报错：不认识的效果键」。那行写的是 `quality_up=0.30`，
而 `_calc._parse_effects` 一直照收（别名 -> `buff_quality`）：**插件认，页面不认**。

根因：v1.13.0 把页面的写死清单换成 `_effects.effect_table()` 下发，
而 `as_dict()` 只给了**规范键名**，没给 `EFFECT_ALIASES` 里的旧写法。
页面于是拿着一份「少了别名」的清单去校验，把一行完全能用的配置标红。

规矩：

* 注册表里凡是**解析器会接受**的键，都必须出现在 `effect_table()` 的 `as_dict()` 里
  （现在每行带 `aliases`），否则页面就会误报。加别名的同时要加断言：
  `test_effects_ext.py`「每行都带 aliases」+ `test_editor_ui.js`「旧写法也进白名单」。
* 页面**只接受、不改写**：`ITEM_EFFECT_ALIASES` 只用于认键和写 tooltip，
  绝不把站长写的 `quality_up` 偷偷换成 `buff_quality`。
* 给页面下发清单这类「单一来源」改造，**改完要拿站长的真实配置跑一遍**：
  这次就是他的 `item_defs` 里有旧写法才暴露出来的（实测那行和「锦鲤玉佩」
  解析结果一模一样 —— 洗髓丹是 v1.11.0 之前的遗留行）。

见闻（`hostiles_seen`）的约定：

* 只在**当着玩家的面**发生捕食时记录，记的是**凶手**（`winner`）的鱼种 id；
  `_resolve_tank_conflicts` 因此返回三元组 `(文案, 有没有变, 被看破的鱼种)`，
  调用点（`水族馆 放`）负责并进玩家数据 —— 别在结算函数里直接改玩家字典。
* 展示只在 `/钓鱼 查 <鱼名>`（他要求的入口）。**不要**顺手加进图鉴/背包，
  那些是共享 helper，一行一行改容易漏。
* 老存档没有这个字段 -> `_calc` 读档时补空表，老玩家开局同样是「不知道」。

### 12. 「展示类收益」必须按时间算，不能按当前状态算（v1.16.0）

水族馆的展出加成（`aquarium_bonus`，取出/卖出时 ×1.2）踩了两次同一个坑：

1. v1.x 早期：每次取出都加一次 -> 「取出→放入→取出」无限刷钱，用 `pond_claimed` 锁成终生一次；
2. v1.16.0 之前：**放进去一秒再取出来照样算一次**（站长报的「那 1.2 的倍数不能立刻
   放入取出就有」）——「只能领一次」根本挡不住这个。

现在的规则：鱼进缸时记 `tank_since`，出缸时把这段时长**累加**进 `tank_seconds`，
取出/卖出时要求 `tank_seconds >= aquarium_bonus_min_hours × 3600`；
不够就返回 `too_new`、**不打 `pond_claimed`**（放回去接着攒，累计制）。

坑与约定：

* ⚠️ `_repair_instance` 是**白名单式重建**：`tank_since` / `tank_seconds` 必须列在里面，
  漏了就会每次读档把计时清零 = 漏洞原地复活。新加实例字段时先想这件事。
* ⚠️ **不要在 `_claim_aquarium_bonus` 里写「没计时就放行」的老存档特例**：
  任何绕过「放入」直接写进缸里的鱼都会白拿加成（单测里就撞见过）。
  老存档迁移放在 `_load_player` -> `_migrate_tank_display()`，一次性补计时，
  之后运行期规则是干净的「够不够时间」。
* 视图里算进度要用 `_tank_display_seconds()`（含「这次还待在缸里」那段），
  直接读 `tank_seconds` 只有上一次结清的量，看起来永远不动。
* 页面/文案只说现象与门槛，别把内部字段名写进玩家可见文本。

**同款漏洞已在 v1.18.0 一起修掉**：`_pond_income(player, cfg, now)` 把「当前馆藏估值 ×
距上次领取小时数」换成「每条鱼按 `max(它进缸的时刻, 上次结算时刻) → 现在` 各自加权」，
空缸期间谁都不产出。`tank_seconds`（累计展出时长）随 ×1.2 加成一起删掉了，
现在只需要 `tank_since`。视图的「现在可领」也必须调**同一个** `_pond_income`，
口径分家就会再次出现「列表说能领、真领却没有」。

### 13. v1.18.0 踩到的几个坑（都很容易再犯）

1. **改默认值要同时改 schema**：运行时的配置是 `_conf_schema.json` 生成的，
   `DEFAULTS` 只是兜底。改了 `_game_data.BUTTON_DEFS_DEFAULT` / `item_defs`
   却忘了同步 schema 的 `default`，就会出现「代码里改了、跑起来没变」（这次就中了）。
   改完用一句话自查：`schema[key]["default"] == DEFAULTS[key]`（内容表按字节比）。
2. **短命令的参数形状**：`fishing()` 里 `after_sub = a2 + after_first`
   （`after_first` 是 rest[1:]，**不含 a2**）。短写法里 a2 就是第一个参数，
   所以路由时一律传 `after_sub`；传 `after_first` 会少一个参数，子命令就回退到「用法说明」
   （这次踩了 4 处）。子命令自己还要防一手：`/钓鱼 买 蚯蚓 3` 与
   `/钓鱼 商店 买 蚯蚓 3` 的 `a2/a3` 形状不一样，路由层负责对齐，别在子命令里猜。
3. **`_expose_globals_all()` 会把 `_calc` 的全局推回旧值**：main 在导入时把 `_calc` 的成员
   复制进自己的 globals，模块末尾又把它推回各兄弟模块 —— 所以任何「`_effects` 写给 `_calc`」
   的运行期状态都会被覆盖。`_calc._effect_allowed()` 现在**直接读注册表**绕开这个陷阱；
   同理，凡是要在运行期共享的可变状态（`BUTTONS` / `BUTTON_EMPTY_SCENES` /
   `BUTTON_COMMAND_EXTRA` / `SUBCOMMAND_WORDS`）都必须是**原地更新**的容器，不能重新赋值。
4. **删空按钮是一条链**：`BUTTONS`（配置里有什么）≠ `_scene_items()`（玩家实际看到什么）。
   后者还会「继承父场景 → 回退出厂」。要让「这个场景就是没按钮」生效，
   必须同时照顾 `_scene_items` / `_scene_buttons` / `_editor_default_buttons` 三处
   （`BUTTON_EMPTY_SCENES`），只改 `main._apply_button_defs` 是半成品。
5. **文案的「整段替换」开关**：`!!` 前缀是给站长的逃生口（放弃 `{原文}` 里的动态内容）。
   `needs_original()` 与 `render_scene()` 两处都要认这个前缀，页面校验也要跟着放行，
   否则会出现「页面说不行、其实插件认」的分裂。
6. **同类不相食**：`_resolve_tank_conflicts` 里比对手之前先比 `fish_id`，
   同种直接 `continue`（连「打了一架」也不该有）。改这段时记得单测里的
   「两条同种狠角色相安无事」与「两种狠角色才打」两条断言要一起过。

### 20. 同一个机制只留一条路径（v1.18.10，连钓与单竿分家的教训）

站长报：「连钓的鱼居然不会跑……连钓最多有鱼没咬饵，这个 bug 很严重」。
两条现象、一个病根：**单竿与连钓各写了一套判定与文案，谁也不管谁**。

| | 单竿 `_do_cast` | 连钓 `_do_cast_multi`（修之前） |
| --- | --- | --- |
| 逃脱 | 弹拉线，手慢/超时 = 必跑（传说 30% 是「没拉到」的概率） | 直接 `random() < spec["escape"]` → 同一批鱼**几乎不跑** |
| 空竿文案 | 空钩 / 深水 / 「咬了一口又吐掉了——蚯蚓 白搭了」 | 只有一句「💨 空竿」 |
| 空竿扣饵 | 被咬掉的照扣 | 一个都不扣 |

结果就是「认真拉线的单竿会跑、连钓不跑」，连钓成了刷传说鱼的捷径；而玩家看到
「连钓从不吃饵」也确实是代码写的。**修法不是各修一处，而是把口径抽成共享函数**：

* `_calc._miss_flavor(bait_id, label, loc, factor)` → `(场景键, 文案, 是否被咬掉)`，
  三种说法（空钩 / `钓点系数 < 0.75` 的深水 / 被鱼咬掉）**只在这里写一次**，
  两条路径都拿它的返回值去 `_say`；
* `_calc._bait_consumed(...)` → 扣饵真值表：`每竿都扣(开关) or 中鱼/杂物 or 被咬掉`；
* `_calc._multi_escape_chance(spec, cfg)` → 连钓专用惩罚：`标称逃脱率 × multi_escape_mult`
  （默认 2.5，封顶 0.95 —— 连钓里也不该存在「必跑」）。**默认值必须让手感变狠**
  （1.0 = 旧行为），否则老配置升级后等于没修；
* 跑掉的那条要**把实际用的概率写出来**（`逃脱率 75%`），不然玩家没法判断是运气还是配置。

自查一句：**「这个机制在另一条路径（单竿 / 连钓 / 批量）上是怎么走的？」**
只要答案不是「同一个函数」，就迟早会出现同一批鱼两套概率 —— 而且会先被站长发现。

⚠️ 静态检查的连带坑：场景键（`cast.miss_*`）现在只在 `_calc.py` 里出现字面量，
`test_local.py` 第 [18] 组扫「死场景」的 `_src_all` 必须把 `_calc.py` 也带上，
否则三个明明在用的场景会被判成死代码。

⚠️ 写用例的连带坑：像 `LOCATION_HOOK_FACTORS` 这种**模块级字典**是「最后一个造出来的
插件说了算」（`_refresh_config` 原地 `clear()` + `update()`），不是挂在 `self.cfg` 上。
所以同一段用例里造第二个插件，会顺手改掉第一个插件后续的判定 ——
`[6l]` 里「咬掉（0.9）」必须在造出「深水（0.5）」那个插件**之前**跑完，
否则连钓会被判成「鱼不开口」、饵一个不扣（这次就是这么红的）。
凡是 `self.cfg.get(...)` 之外的口径，用之前先确认它存在哪。

### 19. 「按次数算」的东西，连钓路径要按竿数循环（v1.18.9）

站长报：连钓 15 次，锦鲤玉佩只掉 1 竿额度 —— 等于白吃 14 竿手气。

原因：`_engine._do_cast_multi` 在循环**外面**调了一次 `_consume_luck(player)`，
把「整批」当成「一竿」；而体力、鱼饵都是按 `planned` 扣的 —— 同一个方法里两套口径。

**现在的规矩**：凡是「消耗 / 剩余次数」类的东西，在连钓里都必须**循环内结算**：

* `luck = _effective_luck(player)` + `_consume_luck(player)` 放在每次 `for index in range(1, planned+1)`
  的最前面（空竿、杂物也算一竿，和体力/鱼饵一致）；
* 一次性手气（插曲/彩蛋）因此天然只作用于第 1 竿 —— 这正是想要的语义；
* 结果里要写清消耗了多少：`🎐 锦鲤玉佩：本批 -N 竿　还剩 M 竿`（用完写「（用完了）」），
  没有 buff 时不显示这一行（不占版面）；
* 加新机制时自查一句：**「这个东西在连钓里该怎么算？」**
  —— 按竿数算的（体力/饵/手气/掉落计数）放循环里；按整批算的（扣费上限、背包余量）放外面。

### 18. 升级默认值不能覆盖站长改过的东西（v1.18.8）

站长反馈：「更新插件不要把我以前的配置重置，我老是要去改」。
`defaults_sync_mode=auto` 以前是「指纹变了就把所有同步项写回新默认」——他手改的数值全被冲掉。

**现在的规矩**（`main._sync_defaults`，改同步逻辑前必读）：

1. `user_edited_keys`（编辑器每次保存都会记一笔）里的键**一律跳过**；
2. 容器类配置**合并**：`DEFAULTS_MERGE_MAP_KEYS`（`键:值` 映射，如
   `location_hook_factors` / `bait_hook_rates` / `rarity_*`）按**键**补缺，
   `DEFAULTS_MERGE_LIST_KEYS`（真列表，如 `quality_weights`）与
   `DEFAULTS_MERGE_NUMBER_TEXT_KEYS`（`tier_base_values` 这种 `1,2,3` 文本）按**长度**补尾巴。
   → **新增钓点/新增品质档位必须走这三类之一，否则到不了老配置**；
3. 官方改了默认值的「整串」配置登记到 `DEFAULTS_VALUE_FIXES`（键 -> ((旧默认, 新默认), ...)），
   只有当前值**逐字等于旧默认**才替换 —— 这次品质档位表改名就靠它；
4. 还有一条兜底：如果 `user_edited_keys` 是空的（第一次启用这套机制），
   就认为「和新默认不同的值」都是站长改过的，**全部保留**并记进清单。
   代价：这次官方改过、又没登记进 VALUE_FIXES / 合并键的默认值不会自动生效 ——
   **所以改了默认值一定要顺手登记**（`test_local.py` 的 `[10t]` 段把这几条都钉住了）。
5. `defaults_sync_mode`：`auto`（默认，上面这套）/ `all`（强制重置，站长明确要的时候用）/
   `off`（什么都不动，只更新指纹）。

### 17. 「只能靠某件道具拿到」的东西怎么实现（v1.18.7，神话那次的规矩）

站长要一档「神话」个体品质，**只能洗髓丹洗出来**、自然上钩永远没有。做法与坑：

* **自然抽奖那头把权重写 0 还不够**：`_roll_quality_mult` 原来的默认档是
  `len(weights) - 1`，而「运气值」会把随机点推到 `total` 之外 —— 点溢出时正好落在
  默认档上。所以权重 0 的档必须同时满足两条：`weights[i] == 0` 时**跳过累加**，
  且默认档 = **最后一个权重 > 0 的档**。少改一条，运气爆棚时就会白送神话。
* **钳制值要跟着可配置的最高档走**：`quality_mult` 原先在 `_new_instance` /
  `_apply_quality` / `_repair_instance` 三处写死 `5.0`，加一档 6.0 的话
  洗出来的 6.0 会在下一次读档被削回 5.0。现在统一走 `_calc._quality_ceil()`
  （= `max(5.0, 最高档上限)`）。
* **「唯一产出路径」只留一处**：神话只由洗髓丹分支里的 `quality_myth_chance` 判定，
  命中后**直接取最高档的区间**（不硬编码 6.0），这样站长改 `quality_tiers` 也仍然成立。
* **次数限制挂在「被限制的对象」身上，且必须进白名单**：`reroll_day` / `reroll_today`
  记在**鱼实例**上（跨天靠日期比对自动作废，不需要定时任务）。
  `_repair_instance` 是白名单式重建 —— 漏写这两个字段 = 每次读档把当天计数清零，
  「每天 3 颗」直接失效（`tank_since` 当年就是同一个坑）。
* **被拒绝时不能扣道具**：先判 `_reroll_averse`，厌恶就 `continue`
  （收集起来在末尾说明），扣道具放在真正洗完之后。
* 老配置里的那一行道具（洗髓丹）改了价格/说明，必须登记到
  `_game_data.CONTENT_ROW_FIXES`（内容表不参与默认值同步），否则站长那边永远是旧价。
* 新增的数值键（`reroll_daily_limit` / `quality_myth_chance`）除了 DEFAULTS +
  `_conf_schema.json`，还要进编辑器页面的 `NUMBER_KEYS` ——
  `test_local.py` 第 [16] 组会断言「面板藏起来的键在编辑器里都能改」，漏了直接红。

### 16. 一个字段别装两种寿命（v1.18.5，手气那次的教训）

**症状**：随机插曲给的「下一竿手气」不消失，还和锦鲤玉佩叠着算（站长报的）。

**病因**：`luck_charges` 一个字段同时装了两样东西：

* 玉佩 = **持续 20 竿**（每竿都该加）
* 插曲/彩蛋 = **一次性**（下一竿用完就没）

而抛竿收尾那段是「玉佩还在生效（`buff_casts_left > 1`）就不清储备」——
于是插曲那份被当成玉佩的额度，挂满一整轮，还每竿都加在玉佩上面。

**现在的规矩**（改手气相关代码前必读）：

* `luck_charges` 只装**一次性**的：每次抛竿收尾一律清零（`_calc._consume_luck`），
  不管玉佩在不在；插曲 / 彩蛋 / 扩展都往这里写。
* `buff_quality`（新）+ `buff_casts_left` 装**持续型**：抛竿取值走
  `_calc._effective_luck(player)` = `max(一次性, 玉佩)`——**不叠加**；
  竿数减到 0 时把 `buff_quality` 一起清掉（别留「还剩 0 竿但加成还在」的空 buff）。
* 展示用 `_views._buff_status_line()`：两者同时在时必须写明下一竿按哪个算，
  否则玩家会以为加了两次。
* 写扩展/新道具时照这个分工来：只写 `buff_casts_left` 不写 `buff_quality`
  = 有竿数没加成（`extensions/example_effect.py` 就是模板）。
* 泛化的教训：**一个字段只装一种寿命**。「持续 N 次」和「下一次」必须分开存，
  否则任何「按剩余次数决定要不要清」的判断都会把短寿命的那份续成长寿命。

### 15. 编辑器页面的窄窗口规矩（v1.18.3 / v1.18.4，改页面 CSS 前先看这条）

AstrBot 的插件页是塞在 dashboard 的 iframe 里的，实际可用宽度经常只有
700~1100px（不是站长显示器的宽度）。所以：

* **不要写死表格的 `min-width` + 一堆固定列宽**：宽度一旦超过容器，右边几列就被切到
  横向滚动条外面，站长看到的就是「有些列怎么也看不到」（他报过一次）。
  现在的做法：所有表格都带 `stack` 类、外面套 `.table-wrap.is-stack`，
  `@media (max-width: 1180px)` 里改成「一行一张卡」（`thead` 隐藏、
  `td::before { content: attr(data-label) }`），所以**每个 `<td>` 都必须写 `data-label`**
  —— 漏了的话窄屏那格就没有标签，看不懂是什么。新增表格时照抄
  `renderTableRow` 的写法。
* **不要用视口高度把内容框死**：`max-height: calc(100vh - N)` 在矮 iframe 里会把表格
  压成一条缝。要带下限：`max(360px, calc(100vh - 300px))`（`.table-wrap` 已经这么写）。
* **窄屏断点**：≤1400px 回复页的预览面板挪到卡片下面（右侧固定 330px + 主列会挤坏表格）；
  ≤1180px 表格拆卡片；≤820px 顶栏不吸顶（换行后高度估不准，会压住内容）、
  底部状态栏允许换行（否则右边信息出屏）。
* `.rp-side` 是 sticky 的：必须配 `max-height: calc(100vh - 118px); overflow: auto`，
  否则面板比窗口高时，下半截顶在屏幕外**永远够不着**。
* **长列表别在一行里显示**（v1.18.4，站长报的）：数值页那些「逗号分隔的名单」
  （`location_hook_factors` 16 项、`bait_hook_rates` 8 项、`tier_base_values`…
  都是 `NUMBER_KEYS` 里第 5 位为 `true` 的**文本行**）如果渲染成一整行字符串，
  那一行的 min-content 宽度会把整张表撑开、别的列被挤走。现在的做法：
  `cellHtml` 里 `row.text` 且条目 >3 个（或字符串 >24 字）就渲染成 `.kv-chips`
  小方块（`max-width: 360px` 兜住宽度），编辑时换成 `<textarea class="is-multiline">`
  并**一行一条**（`_split_list_text` 把换行也当分隔符，所以往返安全）。
  配套：`keydown` 里 textarea 的 Enter 必须是换行，提交走 Ctrl/⌘+Enter。
* 测试口径：`test_editor_ui.js` 的「窄窗口布局」段与「长列表」段把上面这些规则和
  `data-label` / `.kv-chips` / `textarea.is-multiline` 都钉住了，
  改页面 CSS 或表格渲染后跑 `node test_editor_ui.js` 就知道有没有破。
* **整页重绘要保住滚动位置**（v1.18.6，站长报的「点一个项再点另一个就跳回顶部」）：
  `render()` 会先 `snapshotScroll()`、渲染完 `restoreScroll()`，范围包括窗口滚动条、
  `.table-wrap` / `.rp-table-wrap` / `.rp-side`。新增「只换一小块 DOM」的局部更新路径时，
  也要自己把 `scrollTop` 存一下（搜索框那条路径就是），否则一样会跳。
  只有**明确要回顶部**的地方（切标签页）才写 `render(false)`。
* **数值页要「算给你看」**：站长提过「升级二次曲线没有推荐值，不知道怎么填」。
  凡是光看名字猜不出该填多少的数值，就在 `numberLiveHint()` 里加一条——
  按当前输入值实时算出结果（和插件侧公式对齐）、给出推荐值与几个档位的效果对比。
  升级曲线那三行已经这么做了，加新提示时记得同步 `_conf_schema.json` 的说明。

### 14. 存储：AstrBot KV 本来就是 SQLite，别再引第二套库（v1.18.1）

站长提过「改用 sqlite 存数据」。查过真实运行环境后确认**已经在用 SQLite**，
所以没有换存储 —— 自己再开一个库只会多一份要备份/要迁移/会读脏的数据，
而且会绕过 AstrBot 的 KV 接口（`get_kv_data` / `put_kv_data`）。

* 数据位置：`<AstrBot 根>/data/data_v4.db`，表 `preferences`
  （`scope='plugin'` / `scope_id=<插件id>` / `key=<键>`），插件侧的键是
  `player_<uid>` / `player_index` / `leaderboard`。
* **值的形状要照实抄，别想当然**（这次差点写错，靠只读查真库才发现）：
  * 行是 `{"val": <值>}`，而**旧作用域里的 `<值>` 是一个 JSON 字符串**
    （不是嵌套对象）：`{"val": "{\"user_id\":\"10001\",\"gold\":90,...}"}`。
    ⚠️ 写文档时**别把真库里的 uid / 昵称抄进来**（这里是编的 id）：那是玩家的 QQ 号，
    仓库要公开的话就成了泄露。
    所以 `unwrap_kv()` 之后**还要再 `json.loads` 一次** ——
    只按「dict 里取 data」写，扫描出来全员金币 0（页面看着像数据坏了）。
  * 当前作用域的那个字符串里是**信封**（`__fishing_player__` + `data`）；
    旧作用域里是**裸玩家 dict**（`data_version: 3`，没有信封）。
    两种都要认：读摘要用 `parse_player_value()`，搬运用 `normalize_player_value()`
    （裸 dict 会先包成信封，否则页面/存档那条只认 dict 的链路看不见这名玩家）。
  * `player_index` 的 `<值>` 也是 JSON 字符串（`"[\"id1\",\"id2\"]"`），
    `_legacy.as_id_list()` 两种写法都认，写回时保持原格式。
  * 真库里还有 `player_<@A1B2C3D4...>` 这种**脏键**（uid 被打成了「@某人」）：
    `normalize_uid()` 取里面的干净 id 再落地，否则搬进来就是一条永远读不到的废数据。
    （例子里的 id 是编的 —— 文档里不要出现真 uid / 昵称。）
* **插件 id 变了 = 老数据变成孤儿**：作者名从 `dhhxfggg` 改成 `dhhxfggg2023` 时，
  `plugin_id` 跟着变，KV 按 `scope_id` 隔离 → 老存档读不到，表现就是
  「那几名玩家的进度突然从头开始」。这不是数据丢了，还在旧 scope 里躺着。
* 找回工具：`_legacy.py`（`legacy_scan` 只看 / `legacy_import` 只补缺的），
  页面入口在「👤 玩家」页右上角「🔍 找回旧数据」。
  * **只读打开主库**：`sqlite3.connect("file:...?mode=ro", uri=True)`，
    老作用域一行都不动、不删（站长明确要求「旧的先留一份」）。
  * 只补 `player_*`，当前作用域已有的**一律跳过**（当前数据优先）；
    导入前自动存一份 `manual` 快照。
  * 读不到库时把原因记进 `_legacy.LAST_ERROR`，页面照实显示
    （「数据库文件不存在：…」），**不许装成「没有旧数据」**。
  * 面板必须**关得掉**（站长反馈过一次「关不掉」）：扫描结果缓存在
    `self._editor_legacy_cache` 里并随 `editor_status.legacy` 每次下发，
    所以只清页面状态没用 —— 得配一个 `legacy_clear` 动作把插件侧的缓存也清掉，
    否则刷新一次页面又冒出来。这个动作**只清缓存，不碰数据**。
  * `player_index` 要**合并**而不是覆盖（见上面的字符串形状）。
* 新增/修改 `player_*` 之外的老键（`leaderboard` 等）目前**不导入**：
  排行榜是缓存，重算就行；真要导入得先想清楚合并规则。
* 测试口径：`test_local.py` 的 `[10q2]` 段用沙箱里的假库（含信封 + `{"val":...}`）
  覆盖「只读同名插件的旧 scope / 标出缺谁 / 只补缺的 / 索引合并 / 老库零改动 /
  重复导入不写第二遍」——**绝不允许**在测试里连真实 `data_v4.db`（哪怕是读）。
